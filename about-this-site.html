How This Site Was Built

Every page here is hand-written HTML, CSS and JavaScript. No framework, no build step, no package manager, no dependencies to install. This page explains why that was the right choice and what it cost.

Why no framework

The default answer for a portfolio in 2026 is a site builder or a React template. I went the other way deliberately, for three reasons.

A portfolio about engineering should be engineered. It would be a strange thing to publish pages arguing that you should understand your own tools, built on a stack I could not explain. If someone asks me why the navigation is sticky, what the Kalman filter in the flume tracker is weighting, or why the lap solver needs three passes, I should be able to answer all three. Hand-writing the site keeps that true.

A static site is the correct engineering answer to this problem. The requirement is a set of documents with some interactive figures, read mostly once by each visitor, updated by one person a few times a month. That requirement does not need a runtime, a bundler, a hydration step or a dependency tree. Reaching for those anyway would be solving a problem I do not have, which is the same instinct as adding suspension sliders to a point-mass lap model.

It has to still work in two years. A static page with no dependencies has nothing to rot. There is no lockfile, no deprecated transitive dependency, and no build that stops working because a tool went to a new major version. The cost of that is paid up front in typing, which is a cost I would rather pay once.

The stack

Markup and stylingHand-written HTML5 and CSS. One shared stylesheet across every page, built on CSS custom properties and CSS Grid. No preprocessor, no utility framework, no CSS-in-JS.
InteractivityPlain JavaScript in two files, sim.js and montecarlo.js, loaded directly by the page with defer. No bundler and no transpilation, so what the browser runs is the file in the repository, line for line.
Charts and figuresStatic plots generated in Python with Matplotlib, committed as PNG. Interactive plots drawn to a <canvas> by my own code. No charting library.
FontsThe system font stack. No webfont request, so no layout shift waiting on one and no third-party font host.
Hosting and deploymentGitHub Pages, served from the main branch of a public repository. Deployment is git push. There is no CI pipeline, because there is nothing to build.
AnalyticsGoatCounter, loaded asynchronously. Cookieless, no personal data, no cross-site identifier, and the only third-party request on the site.

What I actually had to get right

Writing the markup is the easy part. Four things took real attention.

Porting a physics solver from Python to JavaScript

The lap time model was written and validated in Python, and the interactive version re-solves it in the browser whenever a slider moves. That meant reimplementing the solver in a second language and getting the same answer out of it, which is a more demanding problem than it first looks: the two implementations have to agree to the point where any difference is floating-point noise rather than a difference in the physics.

The discipline that made it tractable was keeping the numerics separate from the drawing code, so the solver could be checked against the Python output on fixed inputs before any of it was wired to an interface. A result that changes when you redraw it is not a model.

Accessibility, on purpose rather than by accident

Every page has a skip link, a single h1 and a heading order that does not jump levels, text alternatives on every image, visible focus styles via :focus-visible, and semantic landmarks rather than a page of unlabelled div elements. Interactive figures carry text alternatives describing the result, so the content survives if the canvas does not render. Animation is suppressed under prefers-reduced-motion.

The part most often skipped is colour. Figures are not encoded by colour alone, and the one status colour on the site ships with an icon and a text label beside it.

Making it findable and shareable

Each page carries its own meta description, canonical URL, Open Graph and Twitter card tags, so a link pasted into LinkedIn or an email renders as a card rather than a bare URL. The homepage includes JSON-LD Person structured data. There is a sitemap.xml, a robots.txt and a styled 404 page that routes back into the site rather than dead-ending.

Keeping it fast without trying very hard

The homepage is about 43 KB of HTML, CSS and icon before images. Images carry explicit width and height so nothing reflows as they arrive, everything below the fold is loading="lazy", and video is preload="metadata" so a page with four clips on it does not pull megabytes nobody asked for. None of that is clever. It is just the default behaviour you get when there is no framework between you and the browser.

Learning the workflow

I had no web development background when this started, and no Git background either. Publishing is now three commands, and understanding what they do mattered more than memorising them: a commit is a snapshot with a message explaining why, and a push makes the snapshot the published one. The same discipline that applies to a model also applies here, which is that a change you cannot describe is a change you should not have made.

Limitations, and what I would do differently

  • There are no automated tests. The JavaScript solver was checked against the Python output by hand on fixed inputs, which caught the errors that mattered, but there is nothing stopping a future edit silently changing a result. A small test file asserting a handful of known lap times is the obvious next step and does not exist yet.
  • Shared markup is duplicated. The navigation and footer are copied into all eleven pages, so a change to either is an eleven-file edit. That is the honest cost of having no build step: I traded a template system for repetition, and every page footer on this site is evidence of the trade. At thirty pages it would be the wrong call. At eleven it is still cheaper than a toolchain.
  • Dark mode only. The site does not respond to prefers-color-scheme, so a visitor who prefers a light interface does not get one. That is a gap rather than a decision.
  • The navigation wraps on narrow screens. It stays usable and readable down to small phone widths, but below roughly 720 px the links reflow onto a second row instead of collapsing into a menu. It works. It is not elegant.
  • No cross-browser test matrix. Developed and checked in Chrome and Firefox on Windows, and on mobile Safari. I have not tested it systematically across versions, so I would not claim more than that.

Relevant skills

  • Taking a project from nothing to deployed and publicly accessible, including the hosting and the release process.
  • Reimplementing a validated numerical model in a second language and verifying the two agree.
  • Version control with Git, and a deployment workflow I maintain myself.
  • Building to accessibility and performance requirements rather than treating them as polish.
  • Choosing the simplest tool that meets the requirement, and being able to say what that choice cost.
